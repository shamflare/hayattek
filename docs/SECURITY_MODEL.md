# نموذج الأمن والخصوصية

> المرجع التقني: OWASP ASVS 4.0 (المستوى 2، والمستوى 3 لنقاط الوصول إلى السجلات)، وOWASP API Security Top 10 (2023).
> الالتزام بمعيار تقني **لا يعني** الالتزام القانوني. راجع القسم الأخير.

## 1. الفاعلون والأدوار

| الفاعل | مصدر الصلاحية | يرى هوية المريض | يرى السجلات الطبية |
|---|---|---|---|
| مدير المنصة (`is_platform_admin`) | حسابه | لا (إحصائيات مجمعة فقط) | **لا** |
| مدير منشأة (`org_admin`) | العضوية | لا | **لا** (إلا إن كان طبيباً أيضاً) |
| طبيب (`physician`) | العضوية + Practitioner معتمد | نعم للمسجلين لدى منشأته، أو بموجب موافقة | سجلات منشأته للمسجلين لديها + سجلات الشبكة بموجب `AccessGrant` |
| ممرض (`nurse`) | العضوية | نعم للمسجلين | العلامات الحيوية وملخص الحساسية (لاحقاً) |
| استقبال (`receptionist`) | العضوية | نعم للمسجلين لدى منشأته | **لا** |
| مختبر/تصوير (`lab_staff`/`imaging_staff`) | العضوية | الحد الأدنى لطلبات موجهة لمنشأته | الطلبات الموجهة إليهم والتقارير التي أصدروها فقط |
| المريض | `Patient.user` | نفسه | سجلاته المعتمدة (ليس المسودات) |
| الوصي | `PatientGuardian` فعال | المحمي | حسب نطاق الوصاية وصلاحيتها الزمنية |

## 2. شروط الوصول السريري (تُفحص كلها، لكل طلب، لكل سجل)

1. المستخدم مصادق، والحساب فعال وغير مقفل.
2. العضوية `X-Hayat-Membership` تخص المستخدم وحالتها `active`.
3. المنشأة حالتها `active` (اشتراك غير معلق).
4. الدور يسمح بالفئة المطلوبة (جدول الأدوار أعلاه).
5. للطبيب: `Practitioner.verification_status == verified`.
6. المريض إما مسجل لدى المنشأة (للسجلات المؤلفة داخلها)، أو يوجد `AccessGrant`:
   - `organization == ctx.organization`، و`practitioner` إما فارغ أو يساوي الطبيب الحالي.
   - `starts_at <= now < expires_at`، و`revoked_at IS NULL`.
   - `scopes` يحتوي فئة السجل.
7. السجل نفسه ليس مسودة لمؤلف آخر.

الفشل في أي شرط = **404** للسجل (عدم كشف الوجود) + `AuditEvent(outcome=denied)` للعمليات الحساسة.

## 3. فئات النطاق (Scopes)

`summary` (حساسيات، أمراض مزمنة، أدوية حالية) · `encounters` · `prescriptions` · `labs` · `imaging` · `documents` · `referrals`

## 4. سيناريو مسح البطاقة

1. QR يحتوي رابطاً بتوكن عشوائي فقط. فتحه بدون تسجيل دخول = صفحة "هذه بطاقة صحية من منصة حياة" دون أي بيانات.
2. مستخدم طبي داخل التطبيق يمسح ← `POST /api/v1/cards/resolve` ← يعيد: الاسم، والعمر، والرقم الصحي، وهل المريض مسجل لدى المنشأة، وهل يوجد Grant. **يُسجل في التدقيق.**
3. إن لم يكن مسجلاً: الاستقبال يسجله (Registration)، وبالتالي يصبح مريضاً للمنشأة، لكن هذا **لا يكشف سجلات المنشآت الأخرى**.
4. لرؤية سجلات الشبكة: طلب وصول (موافقة عبر التطبيق، أو OTP، أو تحقق حضوري موثق).
5. البطاقة المبطلة (`revoked`) تعيد "بطاقة غير صالحة".

## 5. المصادقة والجلسات

- كلمات المرور: Argon2id، والحد الأدنى 10 أحرف، مع فحص كلمات المرور الشائعة والتشابه مع البيانات الشخصية.
- قفل مؤقت بعد 5 محاولات فاشلة (لكل حساب + لكل IP) عبر Rate limiting.
- جلسة الويب: كوكي `HttpOnly; Secure; SameSite=Lax`، ومدة 12 ساعة للحسابات الطبية، مع تجديد عند النشاط.
- توكن الموبايل: 256-bit، مخزن كـ SHA-256، وصلاحية 30 يوماً، ويُبطل عند تسجيل الخروج أو تغيير كلمة المرور.
- MFA (TOTP): **إلزامي** للحسابات الطبية والإدارية في الإنتاج (`HAYAT_ENFORCE_MFA=true`)، واختياري في التطوير.
- إعادة تعيين كلمة المرور: رمز صالح لمرة واحدة ولمدة 30 دقيقة، والاستجابة نفسها سواء وُجد الحساب أم لا.

## 6. سجل التدقيق

يُسجل: `patient.view`، `patient.create`، `card.resolve`، `card.revoke`، `record.view`، `record.create`، `record.finalize`، `record.amend`، `document.download`، `grant.create`، `grant.revoke`، `membership.change`، `practitioner.verify`، `auth.login`، `auth.login_failed`، `access.denied`، `export`.

الحقول: الفاعل، والعضوية/المنشأة، والعملية، ونوع الهدف ومعرفه، ومعرف المريض، والنتيجة، والـIP، والـUser-Agent، والوقت. **لا نصوص طبية.**
الجدول محمي بـTrigger يمنع `UPDATE` و`DELETE`.
المريض يستطيع رؤية "من وصل إلى ملفي" (الجهة، والطبيب، والوقت، ونوع العملية).

## 7. رفع الملفات

- قائمة بيضاء للأنواع: PDF، JPEG، PNG، WEBP، HEIC، TIFF، DICOM (`application/dicom`، يُخزن فقط في الإصدار الأول).
- فحص magic bytes، والحد الأقصى 25MB في الإصدار الأول (قابل للضبط)، واسم التخزين UUID (لا يُستخدم اسم المستخدم).
- bucket خاص، وروابط موقعة 60 ثانية، و`Content-Disposition: attachment` لغير الصور وPDF.
- واجهة `MalwareScanner` (ClamAV في الإنتاج). الملف يبقى `pending` حتى ينتهي الفحص في الإنتاج.

## 8. حماية الـAPI

- BOLA/IDOR: كل `get_object` يمر عبر QuerySet مفلتر من محرك الصلاحيات، وليس `Model.objects.get(pk=...)`.
- Mass assignment: Serializers بحقول صريحة، والحقول السياقية (المنشأة، والمؤلف) من السياق وليس من الطلب.
- Rate limiting: تسجيل الدخول 5/دقيقة، وOTP 3/10 دقائق، وحل البطاقة 30/دقيقة، والعام 600/دقيقة.
- الأخطاء: رسائل عربية عامة للمستخدم، ولا stack traces في الإنتاج.
- السجلات (logs): JSON منظم، ومرشح يزيل حقول PHI المعروفة، ولا body للطلبات.
- CORS مغلق افتراضياً (الويب same-origin والموبايل لا يحتاج CORS).
- HSTS، و`X-Content-Type-Options`، و`Referrer-Policy: same-origin`، وCSP صارمة في Next.js.

## 9. البيانات في بيئة التطوير

بيانات اصطناعية فقط (أسماء من مولد اصطناعي واضح، مثل "مريض تجريبي"). أوامر `seed_demo` ترفض العمل إن كان `DEBUG=False`.

## 10. إجراء الطوارئ (Break-glass) — مؤجل عمداً

لم يُنفذ. المتطلبات المقترحة قبل تنفيذه: موافقة قانونية، ودور خاص، وسبب نصي إلزامي، ومدة قصيرة (ساعتان)، وتنبيه فوري لمدير المنشأة والمريض، ومراجعة لاحقة إلزامية، وتقرير شهري.

## 11. قائمة مراجعة قانونية قبل الإنتاج (تحتاج قرار المالك ومستشاراً قانونياً)

- [ ] الإطار القانوني السوري لحماية البيانات الشخصية والصحية، ومتطلبات ترخيص الجهة المشغلة.
- [ ] مكان الاستضافة: داخل سوريا أم خارجها؟ وهل يُسمح بنقل البيانات الصحية عبر الحدود؟
- [ ] صيغة موافقة المريض على الانضمام للشبكة، ونموذج الموافقة الورقي للمرضى بدون هاتف.
- [ ] فترات الاحتفاظ بالسجلات الطبية وسجلات التدقيق.
- [ ] حقوق المريض: الاطلاع، والتصحيح، والتصدير، وحدود الحذف للسجلات الطبية.
- [ ] آلية التحقق من الأطباء: نقابة الأطباء ومديرية الصحة والوثائق المطلوبة.
- [ ] الوضع القانوني للوصفة المطبوعة ورمز التحقق، والتوقيع الإلكتروني.
- [ ] وصاية القاصرين: سن الاطلاع المستقل والحالات الخاصة.
- [ ] إجراء الطوارئ (Break-glass).
- [ ] عقود معالجة البيانات مع أي مزود خارجي (SMS، استضافة، OCR).
